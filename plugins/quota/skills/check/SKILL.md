---
name: check
description: Quota left on Claude and ChatGPT subscriptions behind CLIProxyAPI vs an even-spend target, plus Claude account rebalancing. Run `subquota` before big fan-outs or bulk LLM jobs, when picking a model family or account, or when asked about quota.
---

Run `subquota` (~0.1s, on PATH from this plugin; named so it doesn't collide with macOS's `/usr/bin/quota`). `subquota --dry-run` shows the Claude weights a rebalance would set; `subquota --rebalance` sets them. A SessionStart hook runs `subquota --quiet`, so the report is usually already in context.

Reading it: `97% vs 83% (+14)` = weekly % left vs the % left if spent evenly, and the slack (negative = ahead of pace). Numbers are the account-wide rate-limit headers as of the last proxied request (`seen`). `← this session` marks the account CLIProxyAPI has bound this session to (recorded by claude-mitm's addon from the proxy's `X-CPA-TRACE-ID` header; absent until the session's first proxied request, so the SessionStart report never shows it). Big slack near a reset will be lost: lean on that account or family. Ahead of pace on GPT: prefer Claude workers, and vice versa. When any account's slack is 0 or negative, the report adds an `At or ahead of pace:` line naming it: tell the user in one line in your first reply of the session, then don't repeat it. Let it shape model choice.

Rebalancing: `subquota --install-launchd` runs `--rebalance` every 15 min via CLIProxyAPI's `PATCH /v0/management/auth-files/fields`, logging changes to `~/Library/Logs/quota-rebalance.log`. With that installed, don't hand-edit weights; change the settings in `~/.config/quota.env` instead (defaults are at the top of the script). During a heavy fan-out, run `subquota --rebalance` yourself. Policy: weight ∝ headroom ÷ hours to reset, floor 10, 0 with no headroom. Headroom is an account's remaining quota, except that `QUOTA_PROTECTED_EMAIL` (the main account that must not run out) keeps back max(15%, its target). If no account has headroom, the protected one takes everything. Weights are session-affine, so changes only steer new sessions.

Fable: Fable 5.2 has its own weekly cap on top of the account's, seen only in Fable responses as the `Anthropic-Ratelimit-Unified-7d_oi-*` headers (stored under `model_quotas` for the Fable model). Each Claude line ends `Fable N% left`, or `Fable blocked, back in Nh` once the cap rejects. When an account is Fable-blocked, CLIProxyAPI cools it down for Fable only (`model-level-cooling`) and fails a session's Fable request over to another account, rebinding the session there (`session-affinity-rebind-on: any`). Weight 0 takes an account out of that pool, so the bound session gets `503 auth_not_found: no auth candidates` instead. So while any account is Fable-blocked, the rebalance gives every account that could serve Fable at least the floor ("Fable fallback"), unless it is at or below its hard reserve (15% for the protected one), and the report adds a `Fable blocked on …` line: tell the user in your first reply, as with the pace line. A session stuck on a blocked account recovers on its next Fable request after the rebalance; nothing needs restarting.
