---
name: check
description: Quota left on Claude and ChatGPT subscriptions behind CLIProxyAPI vs an even-spend target, plus Claude account rebalancing. Run `subquota` before big fan-outs or bulk LLM jobs, when picking a model family or account, or when asked about quota.
---

Run `subquota` (~0.1s, on PATH from this plugin; named so it doesn't collide with macOS's `/usr/bin/quota`). `subquota --dry-run` shows the Claude weights a rebalance would set; `subquota --rebalance` sets them. A SessionStart hook runs `subquota --quiet`, so the report is usually already in context.

Reading it: `+14% headroom  claude/name: weight 100, 97% left (pace 83%), …` leads with the verdict: weekly % left (it ticks down as you spend) minus the % that spending evenly to the reset would leave. `+N% headroom` = slack; `-N% over pace` = spending too fast; `on pace` = within half a point. Numbers are the account-wide rate-limit headers as of the last proxied request (`seen`). `← this session` marks the account CLIProxyAPI has bound this session to (recorded by claude-mitm's addon from the proxy's `X-CPA-TRACE-ID` header; absent until the session's first proxied request, so the SessionStart report never shows it). Big slack near a reset will be lost: lean on that account or family. Over pace on GPT: prefer Claude workers, and vice versa. When any account's slack is 0 or negative, the report adds an `Over pace or at it:` line naming it: tell the user in one line in your first reply of the session, then don't repeat it. Let it shape model choice.

Rebalancing: `subquota --install-launchd` runs `--rebalance` every 15 min via CLIProxyAPI's `PATCH /v0/management/auth-files/fields`, logging changes to `~/Library/Logs/quota-rebalance.log`. With that installed, don't hand-edit weights; change the settings in `~/.config/quota.env` instead (defaults are at the top of the script). During a heavy fan-out, run `subquota --rebalance` yourself. Policy: winner takes all. Each Claude account can keep back a reserve for people using it outside the proxy (`QUOTA_RESERVES="email=pct,…"`, e.g. 10% of the main account for the claude.ai web app, 5% of a shared one), and its target runs down to that reserve instead of 0, so the report's target and slack include it (`keeps N%`). If any account has slack, the one with the most slack per hour to reset gets weight 100 (slack about to be lost at a reset goes first); if every account is over pace, the one least far over gets it. Every other account with quota left gets the floor, 1 (`QUOTA_FLOOR`: in the proxy's failover pool, ~no new sessions). A reserve is a last resort, not a wall: an account inside it has negative slack and loses to any account that isn't, and when all are inside, the reserves drain evenly. 0 only with nothing left; an account with no reading (after a proxy restart) gets 10 (`QUOTA_FLOOR_UNREAD`) so it serves a request soon and can be read. The winner can switch every 15 minutes as its slack is spent; that's expected. Weights are session-affine, so changes only steer new sessions. Bindings are per session and per model (key `provider::session::model`), so a Fable failover moves only that session's Fable requests. Subagents send their parent's session ID (plus their own agent ID), so `← this session` cannot tell them apart. With `routing.session-affinity-subagents: true` a subagent reuses its parent's binding; it is `false` here since 2026-11-15, so each subagent picks its own account by weight. Forked subagents share the parent's binding either way (checked in the CLIProxyAPI 8.0.61 source, `sdk/cliproxy/auth/selector.go`).

Fable: Fable 5.2 has its own weekly cap on top of the account's, seen only in Fable responses as the `Anthropic-Ratelimit-Unified-7d_oi-*` headers (stored under `model_quotas` for the Fable model). Each Claude line ends `Fable N% left`, or `Fable blocked, back in Nh` once the cap rejects. When an account is Fable-blocked, CLIProxyAPI cools it down for Fable only (`model-level-cooling`) and fails a session's Fable request over to another account, rebinding the session's Fable requests there (`session-affinity-rebind-on: any`). Weight 0 takes an account out of that pool, so the bound session gets `503 auth_not_found: no auth candidates` instead; that is why the rebalance gives 0 only to an account with nothing left. When an account is Fable-blocked the report adds a `Fable blocked on …` line naming where its sessions fall back to: tell the user in your first reply, as with the pace line. A session on a blocked account moves on its next Fable request; nothing needs restarting.

Fable reserve: an account's last N% of its Fable cap (`QUOTA_FABLE_RESERVES="email=pct,…"`) is a last resort too. While it is inside that and another Claude account can still serve Fable (not blocked, not held, Fable left over 1% and over its own Fable reserve), `--rebalance` adds `claude-fable-*` to that credential's `excluded_models` (via the same PATCH), so the proxy drops Fable from its model list and Fable sessions fail over; the report line then ends `(Fable reserve held: last resort only)`. It releases the hold when no other account can serve Fable, or at that account's Fable reset (saved in `~/.cache/quota/fable-holds.json`, because the exclusion hides the account's Fable reading). The auth-files listing does not show `excluded_models`; check the auth file in `~/.cli-proxy-api/` or `GET /v0/management/auth-files/models?name=<file>`. To release a hold by hand, drop the account from `QUOTA_FABLE_RESERVES` in `~/.config/quota.env` and run `subquota --rebalance`; a hand-edited exclusion would be put back on the next run.
