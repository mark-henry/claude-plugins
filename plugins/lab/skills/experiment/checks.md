# The rules in full, and what shows each

For each of `lab:experiment`'s thirteen rules, under the same number: the conditions and exceptions the short form in [SKILL.md](SKILL.md) leaves out, then the evidence to open, at launch and at quote. This file is the standard the supervisor (the fresh agent of the skill's Sign-off section) rules by. `prereg.py` is in this directory. "Evidence" alone means the same evidence at both moments. Rerun a check rather than read its old output.

## Pinned

*Pinned* means committed. A file kept out of the repository is pinned by a line `<experiment> <path> <sha256>` written by a script at the time into a commit, or into a log whose past entries the experimenter cannot change (a remote that refuses force-pushes, a tracking server). *Before a run* means the pin's commit is an ancestor of the run's commit, or its line precedes the run's in that log. The run record's `prereg` and plan fields carry the pinned hashes. Two pinned records that give one arm and metric different intervals, with no amendment between them: rule 2 is not met. A hash-pinned file is never overwritten: an amendment, a waiver line or a `close` makes a new version, pinned in turn, and the earlier version is kept for the supervisor to diff. A file's timestamp, a commit's date, or a hash stored inside the file pins nothing.

## Rules 1–8: the design

1. **One difference.** A matched value says which arm it was tuned on. A reused earlier arm is first retrained from its plan at the treated arm's commit, and the retrain lands within rule 4's floor of the earlier value. *Launch:* a diff of the two arms' resolved configs and commands shows only what the prereg record's `varies` names; the plan's knob list. *Quote:* the same diff over every run record of both arms (commit, command, config, models, hashes) shows only `varies`, seeds and commits between which no code path differs; their `started` times interleave, or with one run per arm the gap is in the knob list.
2. **Prediction and denominator first.** For a two-sided question the treated-minus-untreated difference may be predicted as "no direction", with the smallest effect that would count, stated in the decision; every arm keeps its own interval. An arm added later is added by amendment and pinned before its own first output on the items the counted run scores; the record says what screening on other items showed. *Evidence:* a non-exploratory prereg record that `prereg.py open` accepted, present with its current frozen hash in the tree at the commit of every treated run that scored the items the counted run scores (`git show <commit>:<record>`), or pinned by hash before the first such run started when records live outside the repo; the bar text it points to unchanged since.
3. **Controls.** The positive control's stages are the treated arm's: train, merge, sample, score. A rival explanation's control is an arm or check whose failure would show it. *Evidence:* each is an arm with a command; the positive control's scored output shows the pass the plan defined, and its run record shows the same stages as the treated arm's. A reference rung built into the scorer is a baseline only when the same command scores it on the same items.
4. **Noise floor.** Reruns of one checkpoint, or step 0 twice, bound eval noise only and license a claim about these checkpoints on these items. The floor is the largest gap between any two floor runs, unless the plan pinned another statistic before the FREEZE. A measured floor of zero is replaced by the interval over items. *Launch:* the floor runs are named in the plan with their commands. *Quote:* those runs' raw values, recomputed. No floor measured is not met, not a floor of zero.
5. **Leakage and held-out.** Generated training data is training data. If an earlier result on the sealed set shaped this design, the set is dev for this claim. *Launch:* intersect item IDs and content hashes; the ledger of every run that has scored the sealed set; a read of the scorer and sealed items as the optimizer's user fails; one logged call per judge and baseline; failure reports shown to whatever is optimizing carry no gold labels, and its memory and notes carry nothing from held-out items. *Quote:* each counted run scored the sealed set once, at its end; a leak audit of any result above its predicted interval. With no ledger, intersect item IDs with every earlier pack and say that is what was done; a pack reused across studies is dev unless it was declared sealed. Items the instrument was developed on threaten the instrument (rule 6); items the treatment was tuned on threaten the claim.
6. **Instrument.** An LLM judge has an `evals:judge` record (TPR and TNR from a test split run once) valid for this judge model and prompt. A model trained against a judge or reward model is scored by a different, held-out judge from another model family. *Quote:* where the judge record's "Valid for" line does not cover a treated arm's outputs, the expert has re-checked a sample of them. *Evidence:* rerun the fixture, and read its planted fail beside its known pass; the judge record; one logged judge call. *Quote:* where each arm's scores sit against the fixture's pass and fail and against a constant-answer baseline; scores against output length, or the instrument's other known confound. A scorer that is a model is identified by adapter hash and code commit.
7. **Freeze.** With two launch moments, the training FREEZE names what training reads (commit, seeds, train and dev hashes, kill thresholds) and the evaluation FREEZE the rest; each counted run is held to the FREEZE of its own launch moment. The evaluation FREEZE is pinned before any treated checkpoint from the counted training is sampled, and a change to what the training FREEZE named is an amendment. *Evidence:* the FREEZE line and its pin; the scorer and judge-prompt hashes recompute at that commit, the item-set hashes from the stored files; each threshold cites untreated or dev runs, or a chance rate with its derivation.
8. **Run record.** An exploratory run on a dirty tree records its diff instead. A relaunch is a new run naming its parent; a run whose launcher died is closed by a script from its logs. A field the experiment has no use for is null with the reason. A generated dataset has a manifest beside it: source commit, generating command, model and revision, prompt, time. *Launch:* a dry run's record, or the record of a prepare step that the launcher verifies before it runs, its `commit` set and, for a counted run, `git status --porcelain` empty. *Quote:* every field filled or null with a reason, wherever the harness keeps it; each record's pin (`git log --stat`, or the logged hash recomputed); seeds and hashes equal to the FREEZE line, and no code path differs between the FREEZE commit and any counted run's commit; every run reported, killed and relaunched ones included, and the launcher's or job manager's list shows no run without a record.

## Rules 9–13: the result

9. **Nothing moved after the freeze.** An amendment is in the human's own words as a waiver is, and governs runs started after it: results already in hand are exploratory against what it changed. A scorer defect is fixed by amendment and every arm rescored, both scores reported. A step that failed or did not finish, rerun on another machine or in different batches at the FREEZE's commit, seeds and input hashes for every arm, is recorded in that run's record and quoted beside the number, not amended. A step that had finished is not rerun: where two sets of outputs exist and their hashes differ, the first is the result and the second is exploratory. A change to code, scorer, parser or items is always an amendment. With no FREEZE this rule is not met. *Evidence:* `git log` on the plan, scorer and prereg record since the FREEZE, or every pinned version recomputed and diffed against the one before; counted run records per arm equal the FREEZE's seeds and n; `prereg.py close`, run on a copy of the record, succeeds (it refuses changed frozen fields); for each recorded deviation, the two run records diffed and, where both outputs exist, their hashes compared for every arm.
10. **Scores read.** No re-audit is pending. Errored and missing items are counted apart from fails. *Evidence:* the `evals:audit` block naming these run IDs; parse yield k/n. In a harness without `evals:audit`, a written reading stands in when it names the run IDs and the items read (30–50, stratified by score, by a reader not given the hypothesis), covers each contrast the claim credits, and the human who owns the experiment gave the verdict.
11. **Declared denominator, beyond noise.** For a mean, the denominator is the unit and count averaged over. Any other denominator is labeled post hoc. With items as the unit, the difference's interval is paired on shared items. *Evidence:* `prereg.py close` output on a copy (it scores the predictions); a pinned script for every stage that rebuilds the number from run IDs, any bootstrap seed recorded and the interval rerun; rows dropped are counted, with the rule that dropped them.
12. **Confirmatory or exploratory.** A confirmatory number travels as `prereg <file>: predicted X, got Y (n/N)`, a miss or a null included. The counted run a screening run nominates an arm for trains it again. *Evidence:* the label; `git merge-base --is-ancestor`; the draft or message the number is headed for, searched for "preregistered", "confirmatory" and bar language.
13. **The sentence.** *Evidence:* the place it is quoted (the report, the message, the slide), opened; the sentence rebuilt from the artifact: which arm is the comparator, what the unit is, which contrasts met rule 11, how the matched control did, which guards or kills fired.

## The commands

`prereg.py` is called as `python3 <this dir>/prereg.py` (stdlib only).

- `new <record>` writes the template. A bar that does not say its denominator is not frozen: `swarm:brief`, or mark the record exploratory. Each arm's `out` is its run folder relative to the repository root; `num` and `den` are dotted paths into its `report.json`, or numbers; `varies` lists launch-argument names. Optional fields the template omits: `watched` (the code paths that can change a number), `classes` on a metric (each class with its observable test), `reused` on an arm (`commit`, `reason`). Write the script that computes the metrics now, and run it on a synthetic null.
- `open <record>` validates the record, freezes the question, bar, decision, arms, `varies`, `watched`, metrics, predictions, mechanism and surprises (not `status`: read `opened` and the predictions, not the status), and stamps the commit and the uncommitted diff; outside a repository it stamps nothing and still opens. Then pin it.
- `stamp <out_dir> -- <command>` records the commit and the command without running it, before launching an arm whose harness writes no `git` into `launch.json`.
- `parity <record>` compares the arms' launch arguments outside `varies`, their instance-file hashes, their commits and any dirty trees. A design with controls gets one record per contrast, each with its own `varies`; on a failure there, rerun the stale arm at the current commit, or report the failure beside the number.
- `close <record>` prints observed against predicted, hit or miss, on the declared denominators. It refuses a record whose frozen fields changed. An arm of several runs has one `out` folder whose `report.json` the pinned analysis script writes from the runs' reports. It scores each arm's interval, not the difference: write the predicted difference and its paired n in `decision`, and score it by hand beside the output.
- `ls [dir]` lists open records and the calibration over closed ones. Wide intervals that always hit are not predictions.

## What the tools do and do not show

- `prereg.py open` checks that a non-exploratory record has a bar, a decision, and a `[low, high]` prediction and a denominator for every arm and metric. It does not check that an interval could miss, and it refuses only a question, bar or command left as the template wrote it, so the template's example predictions and decision still pass: read every field. Its frozen hash is stored in the record itself: only the record's pin at each such run's commit shows the predictions came first.
- `prereg.py parity` compares launch arguments outside `varies`, the instance files it finds, the commits and any dirty trees. It reads one stamp per arm folder, compares every arm to the first against one `varies` list, and only warns when it finds no instance files, so a PASS is support for rule 1, not proof, and a FAIL on a control arm's declared difference is expected.
- `prereg.py stamp` records the commit, the uncommitted diff and the command. Its `dirty` list ignores untracked files, and a second stamp into one folder overwrites the first: give a relaunch its own folder. `close` and `parity` read only the folder each arm's frozen `out` names, so after a relaunch they see the parent run or nothing: for a relaunched arm do their checks by hand against the final run's record and report.
- `prereg.py close` refuses a record whose frozen fields changed, and scores each prediction as hit or miss. It does not apply the bar. Running it again rewrites the record, so check on a copy.
- An `evals:judge` record is valid for the distribution its "Valid for" line names. An `evals:audit` verdict is a prescreen of how a scorer was applied; its verdicts are never validation labels.
- Where the harness keeps these records in its own format, each check that names a tool is done by hand against the rule: for `open`, read every field; for `close`, diff the frozen fields against their pinned version and recompute each prediction's hit or miss; for `evals:judge`, a record with TPR and TNR from a test split run once. A tool's acceptance is evidence only for the format it was written for.
- A harness's own checker or launcher is evidence only after you have seen a planted-bad input fail it, on a copy.
